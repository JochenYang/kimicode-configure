name: debug
description: 排查 bug、测试失败、构建失败、运行时错误、性能退化或行为不符预期时使用。用户说「这个报错了」「测试挂了」「为什么这里不对」「之前还好好的」「跑不起来」「偶尔失败」时加载。不用于：新功能开发。

请调试 `$ARGUMENTS`（若为空则使用用户当前报告）。用户可在参数中指定 `diagnose`、`fix` 或 `verify`；未提供时根据意图判断。

## 铁律

根因调查完成前不提出修复。没读完错误、没复现、没确认原因之前，不给「先试试这个」；在回复里建议修法也算提出修复。简单 bug 可以一分钟走完流程，但不得跳过。

## 强制流程

1. 读取适用的 AGENTS.md、完整错误信息（整段堆栈，不只第一行）、调用方和最近改动。
2. 检查改了什么：`git diff`、最近提交、依赖/配置/环境差异；有 known-good 提交和可重复的失败命令时，用 `git bisect run <复现命令>` 定位，结束后 `git bisect reset`。
3. 先写出要验证的行为主张，以及主张为假时会失败的最短检查。
4. 复现失败路径；不能复现时记录环境、输入、版本和阻塞原因，先加日志取证，不猜。
5. 多层系统在边界加临时日志（CI → build → deploy、UI → API → DB），跑一次看数据在哪一层变坏；只记录密钥是否设置，不记录值。
6. 隔离变量：缩小到最小输入、最小文件、最小调用链或最小测试。错误在调用栈深处时反向追数据，修在源头而不是崩溃点，见 `references/root-cause-tracing.md`。
7. 在仓库里找做类似事情的正常代码，完整读参考实现或文档，逐条列出正常与异常案例的差异，不假设「这个不可能有影响」。
8. 一次只验证一个假设：「X 是根因，因为 Y」。验证后回退临时改动；失败实验不叠在下一个假设上。
9. 执行最短验证。不确认就回到第 1 步；不把静态猜测当成结论。
10. 若用户要求修复：能自动化的先写最小失败用例，看它按预期失败；再做一处针对根因的最小改动，检查所有调用方和失败路径。
11. 复验原失败路径、正常路径和至少一个边界路径。修复涉及 `docs/plans/<slug>.md` 的 Affected behaviors 时，列出要重跑的 Test plan 条目。
12. 连续 3 次修复失败就停：不再试第四次。列出每次尝试暴露了什么，判断是不是设计问题，和用户讨论重构还是继续。
13. 检查是否留下调试日志、临时文件或无关改动；能防复发的检查点保留，见 `references/defense-in-depth.md`。

## 红牌

出现以下念头就回到第 1 步：

- 「先快速修一下，之后再查」
- 「大概是 X，先改了试试」
- 「改几处一起跑测试」
- 「我不完全理解，但这样可能行」
- 两次失败之后「再试一次」

## 输出格式

```markdown
## Symptom and reproduction
症状；复现命令或输入与结果；不能复现时写环境与阻塞原因

## Isolation
缩小到的最小范围；边界取证结果

## Root cause
根因；证据等级 L1/L2/L3/L4

## Fix
最小改动与失败用例（`diagnose` 模式写「仅诊断，未修改」）

## Verification
- [ ] 原失败路径
- [ ] 正常路径
- [ ] 边界/失败路径

## Ruled out
试过并排除的假设与依据
```

`diagnose` 只诊断不修改；`fix` 可改代码但不自动提交；`verify` 优先复查已有修复，不重复无关重构。无法执行关键验证时，不得宣称修复完成。

细则按需查阅本 skill 目录下的 `references/`（Kimi Code 下可用 `${KIMI_SKILL_DIR}` 定位）：`root-cause-tracing.md`、`condition-based-waiting.md`、`defense-in-depth.md`。
