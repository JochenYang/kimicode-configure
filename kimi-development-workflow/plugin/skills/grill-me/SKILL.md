请对用户指定的任务 `$ARGUMENTS`（若为空则使用用户当前请求）做逐题访谈，直到对目标、范围、验收与关键取舍达成共识。只问清楚，不写开发计划。

## 定位

本 Skill 只负责「问清楚」：产出 `.devflow/<slug>/interview.md`，记录已确认的决策、验收草案、排除的方案与未决项。把共识变成 `.devflow/<slug>.md` 或 `docs/plans/<slug>.md` 是 `change-plan` 的事；访谈中不写计划文件，也不顺手落实现步骤。

本 Skill 需要写 `.devflow/<slug>/interview.md`。写不了（例如 Plan mode 拒绝 Write / Edit）时，把记录完整留在回复里，并提示切换模式后再保存；访谈本身照常进行。

## 与「一轮问完」的关系

默认规则是缺决策时一轮问完、少打扰。用户主动触发本 Skill，就是要求被逐题拷问：**一次只问一题**覆盖那条默认。其余规则不变：能查到的不问、选项不夹带、`(Recommended)` 放第一、提问前写明已知事实。

## 流程

1. **定 slug 与记录位置**。slug 用 kebab-case 任务名；确认 `.devflow/` 已在 `.gitignore`，没有就先加。记录写在 `.devflow/<slug>/interview.md`。该文件已存在时先读它：`aligned` 的决策不重问、不推翻，从 `OPEN` 项继续。
2. **开场先查再问**。读代码、文档、AGENTS.md、git 历史和已有的 `.devflow/` 文件，用 2–3 句复述你已理解的目标与已知事实；然后列出本次要过的分支（见下）和它们之间的依赖，让用户增删。小任务只留两三个分支，不硬凑。
3. **按依赖排序，一次一题**。先问影响范围与验收的上游决策，再问依赖它的下游决策；上游答案变了，回到受影响的下游重问。每次 `AskUserQuestion` 只放一个 question；`AskUserQuestion` 不可用（如 auto 模式）时改用普通文本，仍然一次只问一题，等用户回答后再继续。
4. **每题带推荐答案**。给 2–4 个选项，`(Recommended)` 放第一并写一句理由。选项只提供用户原话留空的选择：不夹带需求、交付物、流程步骤或质量标准；默认项是最接近用户原话的那个；用户的「可以」不写成「必须」；没有哪个选项要求用户已排除的事。开放问题只问一个，不给选项。
5. **能查的不问**。代码库、文档、git 历史、已有 `.devflow` 文件能回答的，自己查；查到的写进记录并标「已查证」。查不到、或查到的是几种可能，才问。
6. **边问边记**。每得到一个答案就回写 `interview.md`，不留到最后一次性写。用户的答案与你的推断分开记；用户改口以最新为准，在该决策下记一行 `改口:`。
7. **用户要跳过直接开工**：推回一次，说明输入不足是结果差的首要原因、哪几个决策没定会让返工变贵；用户坚持就放行，在记录顶部标「按最小输入继续」，未过完的分支进 `OPEN`，`Status` 同样改为 `aligned`（`change-plan` 只认 aligned，OPEN 会被带进 Risks）。
8. **收口**。每个分支都有结论或明确 `OPEN`；`OPEN` 写清由谁答、怎么答（查什么 / 问谁 / 跑什么）。全部过完把 `Status` 改为 `aligned`，把记录的路径原样告诉用户，并说明下一步走 `change-plan` 出计划。

## 分支

按任务裁剪，开场列给用户确认：

- 目标、用户与成功标准：为什么做、给谁用、主要场景、怎么算成功。
- 范围：Must-have、Nice-to-have、明确的 Out of scope；分阶段交付时含里程碑与顺序。
- 验收：行为类用 `WHEN <触发> THEN <可观测结果>`；不可测的写明为什么。
- 技术约束与集成边界：语言、框架、依赖、平台、与其他系统的接缝。
- 安全、合规、性能：涉及认证 / 支付 / PII / 密钥 / 迁移 / 公共 API 时必过。
- 风险、取舍、排除的方案：每个被排除的方案写为什么排除，避免下次重试。

## 产出：`.devflow/<slug>/interview.md`

```markdown
# <任务名> 访谈记录

- Status: draft | aligned
- Date: YYYY-MM-DD
- 按最小输入继续: 是（用户跳过未过完的分支时写此行）

## 已知事实（已查证）
- ...（来源：文件路径 / 命令 / 文档）

## 共识
- Goal: ...
- Why: ...（为什么要做，成功对谁有意义）
- Must-have: ...
- Out of scope: ...
- Decisions:
  - D1: <决策> — <用户给的理由>（用户原话：<...>）
    改口: <原答案> → <新答案>
  - ...

## 验收草案
- WHEN <触发> THEN <可观测结果>

## 排除的方案
| 方案 | 为什么排除 |
|---|---|
| ... | ... |

## 未决（OPEN）
- [ ] <问题> — 由谁答 / 怎么答
```

## 衔接

`Status: aligned` 后，用户说「出计划」「落计划」时走 `change-plan`；它按 `.devflow/*/interview.md` 找到本任务的记录，slug 沿用目录名，aligned 的决策不重问，`OPEN` 项进 Risks。本 Skill 不写 `.devflow/<slug>.md`，也不写 `docs/plans/`。

## 红牌

出现以下念头就回到流程：

- 「一次把几个问题问了吧」——一次一题是用户触发本 Skill 的意义。
- 「顺手把计划也写了」——越界；出计划是 `change-plan`。
